# Viewer configuration

Every viewer takes a typed `data` prop plus a shared configuration covering coloring, formatting,
interactivity and graph layout. Set it once with `ViewerConfigProvider`. Any viewer can override
any field with a prop of the same name.

```tsx
import { ViewerConfigProvider } from "@r4pm/components";
import { wasmViz } from "@r4pm/components/viz/wasm";

<ViewerConfigProvider value={{ viz: wasmViz, colorOf, format, onSelect }}>
  <PetriNetViewer data={net} />
  <DFGViewer data={dfg} colorOf={otherPalette} /> {/* prop beats provider */}
</ViewerConfigProvider>;
```

Every field is optional and falls back to a sensible default, with one exception. Graph viewers need
`viz` to lay out their graphs and to export SVG, because the core does not include rust4pm's
visualization. Without it they place their nodes in a plain row, column or grid. See
[Graph Layout](?path=/docs/getting-started-graph-layout--docs).

## `ViewerProps<T>`

What every registry viewer receives.

```ts
interface ViewerProps<T> extends ViewerConfig {
  /** The typed binding result this viewer renders. */
  data: T;
  /** Source object handle, for drill-down. */
  handle?: string;
}
```

A few viewers are pure renderers with no interactive surface. Those take `StaticViewerProps<T>`
(`{ data: T }`). `colorOf`, `onSelect`, `actions` and `format` do nothing there, and the type says so
before you try.

## `ViewerConfig`

```ts
interface ViewerConfig {
  colorOf?: ColorResolver;
  format?: ViewerFormat;
  actions?: ViewerAction[];
  alignmentStyle?: AlignmentStyle; // "trace" | "deviation"
  onSelect?: (target: ViewerTarget) => void;
  onElementContextMenu?: (target: ViewerTarget, event: { clientX: number; clientY: number }) => void;
  viz?: VizTransport; // rust4pm's visualization: graph layout and SVG export
  routing?: "diagonal" | "orthogonal"; // edge routing of the process maps
}
```

### `colorOf` (`ColorResolver`)

Resolves a CSS color for a domain key. The same activity or object type then looks the same in every
viewer. Return `undefined` to fall back to the built-in deterministic palette.

```ts
type ColorResolver = (scope: string, key: string) => string | undefined;
```

Full guide, with the shade helpers and the scope list:
[Coloring](?path=/docs/getting-started-coloring--docs).

### `format` (`ViewerFormat`)

Shared value formatters. Unset fields keep the viewer's own formatting. Between provider and prop
`format` merges field by field; the other config fields replace wholesale.

```ts
interface ViewerFormat {
  number?: (n: number) => string;
  date?: (ms: number) => string;
  duration?: (ms: number) => string;
}
```

### `actions` (`ViewerAction[]`)

Entries the viewer adds to the context menu of its elements.

```ts
interface ViewerAction {
  id: string;
  label: string;
  icon?: ComponentType<{ size?: number }>;
  scope?: string; // limit to one target kind; undefined = any element
  run: (target: ViewerTarget) => void;
}
```

### `onSelect` and `onElementContextMenu`

`onSelect` reports a plain left-click on an element. `onElementContextMenu` is the escape hatch for
building a fully custom menu instead of using `actions`. Both receive a
[`ViewerTarget`](#viewertarget).

### `viz` (`VizTransport`) and `routing`

`viz` runs rust4pm's visualization bindings, which lay out the graph viewers and draw their SVG
export. Pass the embedded `wasmViz` from `@r4pm/components/viz/wasm`, or a transport to a backend that
runs the bindings. `routing` sets how the DFG, OC-DFG and OCEL type graph route their edges
(`"diagonal"` or `"orthogonal"`). Full guide:
[Graph Layout](?path=/docs/getting-started-graph-layout--docs).

## `ViewerTarget`

The element a host acts on, handed to `onSelect`, `onElementContextMenu` and `ViewerAction.run`.

```ts
interface ViewerTarget {
  scope: string; // element kind
  key: string; // identifies the element within that kind
  data?: unknown; // optional raw payload for richer host handlers
}
```

Scopes emitted today:

| Scope | Key | Emitted by |
| --- | --- | --- |
| `"activity"` | activity name | DFG / OC-DFG node click and context menu |
| `"time-range"` | `"<startMs>/<endMs>"` | dotted chart selection |

Treat `scope` as an open string. Match the ones you handle and ignore the rest.

## Persisted display settings

Viewers keep small display choices in local state: DFG metric and direction, edge cutoff, export row
limit. Wrap them in a `ViewStateProvider` to own that state yourself and a panel comes back the way
the user left it.

```tsx
import { ViewStateProvider } from "@r4pm/components";

<ViewStateProvider viewState={saved} onViewStateChange={setSaved}>
  <DFGViewer data={dfg} />
</ViewStateProvider>;
```

`viewState` is an opaque `Record<string, unknown>`. Persist it as JSON. With no provider the
underlying `useViewSetting(key, initial)` hook behaves as plain `useState` and viewers work unwrapped.
Use the same hook in your own components to keep their settings in the same bag.
